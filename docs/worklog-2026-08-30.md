## 18:20 — CORRECTION: qa_score was already numeric. My earlier report was wrong.

On the 29th I reported `dashboard_calls.qa_score` as still `integer` and said
the migration had not been applied. That was wrong, and it sent the user to run
`supabase db push`, which correctly answered **"Remote database is up to date."**

**Root cause: I read the type from PostgREST's OpenAPI spec at `/rest/v1/`,
which is a cached schema, not the database.** PostgREST reloads that cache on
`NOTIFY pgrst, 'reload schema'` or restart, so it can report a column's old type
indefinitely after a migration lands. Re-fetching the spec does not help — the
staleness is server-side, not in the response.

**How to actually check a live column type with only the service-role key** (no
Postgres password, no SQL access) — make PostgREST cast a probe value and read
the error:

```
GET /rest/v1/dashboard_calls?select=call_id&qa_score=eq.74.5
  integer column -> 400  {"code":"22P02","message":"invalid input syntax for type integer: \"74.5\""}
  numeric column -> 200  []
```

Always run it against a known-integer column in the same table as a control,
or the probe proves nothing. `duration_sec` returned 400 while `qa_score`
returned 200 — so the column is numeric and the migration had applied.

The user's own hypothesis (file missing or unsaved) was also checked and
rejected: the file is present at 3,987 bytes, 82 lines, `alter table` at line 51,
correctly named.

### Gotcha found while verifying: Supabase caps responses at 1,000 rows

My first attempt at counting fractional scores fetched `qa_score` for all
scored rows and counted decimals in the response. It returned **215**, not 596 —
because Supabase sets PostgREST's `max-rows` to 1000, so the response was the
first 1,000 rows, silently truncated. No error, no warning, and 215 is not
absurd enough to look wrong.

This is a sibling of the paging trap already in CLAUDE.md: **a count computed
client-side over a PostgREST response is wrong unless you page to exhaustion
with a unique `order=`.** Correct version pages in 1,000-row windows ordered on
`call_id.asc` and stops on an empty batch — which then returned exactly 4,342
and 596. Anything that needs a total should ask for `Prefer: count=exact` and
read `Content-Range` rather than counting rows it received.
