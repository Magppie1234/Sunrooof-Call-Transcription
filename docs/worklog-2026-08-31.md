### `redFlags` and `reviewReasons` are NOT detail — near miss

They read like per-call audit detail. They are not: `AdvancedQa.tsx` uses them in
its **list** view — a red-flag column, its sort comparator, the CSV export and
the needs-review flag (lines 107, 109, 117, 202). Moving them out would have
emptied a column and a flag **with no error raised and no page broken**. The
failure would have looked like data, not like a bug. Only `criteria` and
`conduct` move.

### The 54 MB import a grep missed — the real lesson of the day

After the split I grepped for `data/real/dataset.json`, found only comments, and
reported "nothing imports the fat snapshots". **That was wrong.**
`src/data/taxonomy.ts` imports it — and because that file sits *inside*
`src/data/`, it writes the path as `./real/dataset.json`, which the pattern
never matched.

The first build after the split still weighed **72 MB and carried all 282,517
transcript turns.** It was caught by measuring the built chunk, not by reading
the code:

```
grep -o 'speaker:' dist/assets/index-*.js | wc -l    282517
```

`taxonomy.ts` needs two top-level keys totalling a few KB, but **a JSON import
pulls the whole file into the referencing chunk**, and `taxonomy.ts` is reached
from `filters.ts` — so the main one.

Two rules worth keeping:
- **Grep for the imported basename, not a path.** A relative path depends on
  where the importing file sits, so a path-shaped pattern silently misses.
- **Verify a bundle-size change against the bundle.** The build is the only thing
  that knows what ended up in it.

## CHANGE — what git tracks was swapped (commit 243250a, NOT YET PUSHED)

The app imports the slim files; none of them were tracked, so a Vercel build
would have failed at import resolution while carrying the 54 MB `dataset.json`
it no longer reads.

- **Now tracked:** `dataset.slim.json` (23 MB), `qa_audits.slim.json` (9 MB)
- **Now ignored:** `dataset.json`, `qa_audits.json` — both regenerable
- **Still ignored, and never to be deployed:** `public/data/detail/`

The detail files stay out for **security, not size**. Files under `public/` are
served as plain static assets at a guessable URL, so authentication in the SPA
cannot protect them: the moment Deployment Protection comes off, anyone who can
guess a call id reads a customer transcript, signed in or not. They come from
`GET /api/call/[id]` behind RLS instead. Until that exists the hosted build
renders Call Detail without its transcript and audit panels, degrading rather
than erroring.

Note this removes `dataset.json` from HEAD, not from history.

## H7 — prove nothing moved

The plan asked for CSV diffs across three pages and a walk of twelve. What was
run instead is a **complete** argument rather than a sampled one, in four parts.

**1. Structural — the slim payloads are the fat ones minus exactly the named keys.**

```
dataset    6,253 records · wrong key shape 0 · value mismatches 0
qa_audits  6,260 records · wrong key shape 0 · value mismatches 0
top-level generatedAt · sourceLabel · employees · taxonomy · corpusSize ·
          auditedCount · model · scorecard   all preserved
```

Every retained field is byte-identical on every record.

**2. Static, exhaustive — nothing that aggregates reads the five dropped keys.**
Every read of `transcript`, `entities`, `recordingUrl`, `criteria` or `conduct`
is in `CallDetail.tsx`, `QaAuditPanel.tsx` (via prop), the `AdvancedQa` drawer
(which fetches detail), or the merge in `realService.ts`. `provenance.ts` names
them only as documentation strings. **None in `metrics.ts`, `alerts.ts` or
`filters.ts`.**

**3. No dynamic access.** Zero occurrences of `Object.keys(c)`,
`JSON.stringify(c)`, `c[…]` or `call[…]` anywhere in `src/` — so nothing reads a
field by computed name, which is the one hole a key-name sweep would leave.

**4. CSV exports carry no whole objects.** `exportCsv(filename, header, rows)`
takes explicit arrays of primitives; every call site names its fields.

Taken together: the inputs to every aggregate and every CSV export are identical
by construction, not by sampling.

### What this does NOT establish

It does not exercise the rendered UI. It proves the numbers cannot have changed;
it does not prove a panel still renders. `tsc -b` passes and the preview serves,
but **the twelve-page walk in a browser has not been done** and should be, by a
human, before this is called finished. The specific things to look at are the
three that changed behaviour: Call Detail's transcript and QA panels, and the
Advanced QA drawer's criteria table.

## Sunday H4 — severing the shell's link to the snapshot

### The blocker, stated precisely

`components/layout.tsx` is the always-loaded app shell, and it imported four
constants from `realService`:

```ts
import { DATA_ANCHOR, DATASET_CALL_COUNT, DATASET_MIN_DATE, DATASET_MAX_DATE }
  from '../services/realService';
```

That is a static edge from the main chunk into `dataset.slim.json`, so the
21.5 MB of call records stayed in the bundle whatever `DATA_MODE` said.

**There was a second edge, and it was the worse one.** `data/taxonomy.ts` also
imported `dataset.slim.json` — to read seventeen employees and eight string
arrays off the top of it — and `lib/filters.ts` imports `taxonomy.ts`. So the
snapshot was pinned into the main chunk twice over, and fixing only the four
constants would have moved nothing. This is the same trap as the first split:
the earlier grep for `data/real/dataset.json` missed `taxonomy.ts` because it
lives inside `src/data/` and so writes `./real/dataset.json`.

Between them: four numbers and eight dropdown lists, **41,413 bytes measured**,
were holding 21.5 MB in place.

### What was built

**Database** — `20260831122500_dashboard_meta.sql`, applied.

| Object | Purpose |
|---|---|
| `dashboard_employees` | 17-row roster. A table, not jsonb, because `employee_id` is what the Agent RLS policy will read and a policy cannot join a jsonb array. |
| `dashboard_snapshot` | Exactly one row — `id boolean primary key default true check (id)` admits no second — holding `generated_at`, `source_label`, `taxonomy`, `geo`. |
| `dashboard_meta` (view) | The two joined with live `count/min/max` over `dashboard_calls`. `security_invoker = true`. |

**The taxonomy is stored, not derived in SQL.** `select distinct region from
dashboard_calls` is the obvious way to build the region list and the wrong one:
`build_ci_dataset.py` already computes these lists with its own normalisation
while joining Zoho, Sarvam and the enrichment files, so re-deriving them here
would give two definitions that agree today and drift the first time the Python
changes. Count, min and max **are** derived live, deliberately — they describe
what is actually in the table, so a disagreement between table and stamp shows
the table's truth.

**Loader** — `load_dashboard_tables.py` gained `employee_rows()`, `geo_rows()`,
`snapshot_row()`, and a `--only {all,calls,detail,meta}` flag, because
`call_detail` is 97 MB and several minutes and reloading it to change seventeen
employee rows is waste. Verification always runs in full whatever was loaded,
and now also reads `dashboard_meta` itself — a row count proves nothing about a
one-row view, since an empty taxonomy and a full one both count as 1.

**Route** — `GET /api/meta`. 41 KB. Returns `minTs`/`maxTs` **raw**; the client
derives the anchor and picker bounds with `deriveCorpus()`, the same function in
both modes. Deriving them behind the API would put that arithmetic in two places
and the entire date filter hangs off it — the same argument `/api/calls` makes
for not reimplementing `matchesDims()` in SQL.

**Front end**

- `data/corpusMeta.ts` — new. The `CorpusMeta` wire type, `deriveCorpus()`,
  `corpusFromCalls()`, `dedupeGeo()`.
- `DataService.getMeta()` — added to the contract; all implementations supply it.
- `data/taxonomy.ts` — rewritten. No dataset import, no mock import, no
  `DATA_MODE`. Exports are `let` (live ES bindings) so all nine importing
  modules are unchanged, and their **initial values are Proxies that throw on
  access**, so a read before load is a stack trace rather than an empty
  `EMPLOYEES` silently narrowing a filter to nothing.
- `state/CorpusMetaProvider.tsx` — new. Resolves `service.getMeta()` once,
  calls `installTaxonomy()` *before* `setCorpus()`, and gates children on it.
- `services/realService.ts` — the snapshot moved behind `await import()`, so it
  is its own chunk rather than part of whatever references the module. The four
  exported constants are gone.

### A latent bug fixed on the way

`layout.tsx` imported `DATA_ANCHOR` and `DATASET_CALL_COUNT` from `realService`
**unconditionally**, including in mock mode. The demo dashboard was therefore
reporting the live corpus's call total and seeding its custom date range from
the live corpus's newest call. `mockService.getMeta()` now supplies its own.

### Verified

- `META PARITY: EXACT` — `/api/meta` compared field by field against
  `dataset.slim.json`: `generatedAt`, `sourceLabel`, `callCount`, `employees`,
  `taxonomy`, `geo` (all 456 triples), `minTs`, `maxTs`. Compared on a canonical
  key ordering, because `jsonb` does not preserve key order and a raw
  `JSON.stringify` would have reported a false failure on every geo row.
- The Python `geo_rows()` ordering was checked row-by-row against the
  TypeScript `dedupeGeo()` ordering rather than assumed — code-point sort vs
  `localeCompare`. Identical on this snapshot: every region and state is ASCII
  and capitalised, and the three non-ASCII values (Dubai, spelt three ways) are
  cities, which are not in the sort key.
- Loader verification, all ten checks green, including `meta anchor
  2026-08-01T13:20:23+00:00` — the bound the 4,655-call window is measured from.

### Two bugs found in `api/_lib/db.js` while wiring this up

Both would have failed only on the new table, and one of them silently:

1. `selectAll()` appended `,call_id.asc` to the order **unconditionally**.
   `dashboard_employees` has no `call_id`, so the request would have 400'd.
2. Worse, its dedupe read `r.call_id` — `undefined` for every employee row, so
   all seventeen would have collapsed to one under the key `"undefined"`, and
   the roster would have come back with a single agent and no error.

`key` is now a parameter defaulting to `call_id`. `selectOne()` was changed at
the same time to take whole PostgREST predicates in a `filters` object rather
than a bare `column`/`value` pair, so a caller that needs something other than
`eq.` does not require a new parameter; `api/call/[id].js` was updated to match.
